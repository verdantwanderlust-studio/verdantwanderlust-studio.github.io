# 更新景觀丸藝官網

## 你在幫誰

Ivy 是這個網站的主人,景觀設計師,**不是工程師**。她不知道什麼是 YAML、commit、branch,也不需要知道。

她要的是「網站上那句話改掉」,不是「編輯 about.yaml 的 body 陣列第二個元素」。所以:

- **用她的語言回話。** 講「關於頁的第二段」,不要講「about.yaml 的 `body[1]`」。
- **不要問她技術問題。** 「要用 webp 還是 avif?」這種問題她答不出來,你自己決定。
- **動手前一句話確認,不要一長串。** 「我要把關於頁第二段改成 XXX,可以嗎?」
- 她說的話可能很模糊(「這裡怪怪的」)。模糊就問,**不要猜著改**。

她用 Claude Code desktop,所以她的電腦上有完整的 repo、能跑 dev server。**這很重要**:你可以直接開預覽給她看,不需要等雲端部署。

## 這個網站的現實(2026-07-17 核實)

搞錯這些會讓你做白工,或做出她碰不到的東西:

| 事實 | 意義 |
|---|---|
| 正式站 = `github.com/verdantwanderlust-studio/verdantwanderlust-studio.github.io` | 這個 repo 就是網站,**push main 會在約 1 分鐘後自動上線** |
| 沒有雲端預覽環境 | 預覽 = `npm run dev` 開 localhost 給她看。這是唯一的預覽 |
| 文字住在 `src/content/pages/*.yaml` | about / contact / courses / home 四個檔。**這是你唯一該改文字的地方** |
| 圖片也住在同樣的 yaml | `hero` / `photos` / `marquee` / `featured` 欄位。改 `src` 就換圖 |
| 視覺數值住在 `src/styles/tokens.css` | 只改**已存在** token 的值 |
| 圖片檔住在 `src/assets/` | Astro 建置時自動壓縮轉 webp,你不用管 |

**沒有的東西**(不要跟她提,提了就是承諾一個不存在的功能):Cloudflare 預覽連結、GitHub Actions 圖片管線、`public/images/`、作品集的 MDX 檔。

## 開始之前:設定

第一次幫她換圖時,你需要知道她的照片放哪。跑:

```bash
node .claude/skills/update-site/scripts/setup.mjs
```

它會掃常見的 Google Drive 位置,找到就列給她確認,找不到就請你問她。答案存進 `.claude/skills/update-site/config.json`(已 gitignore,不會進 repo)。

**只改文字或視覺的話不需要設定,直接做。**

先聽懂她要哪一種。四類:

| 她會說 | 這是 | 去哪一節 |
|---|---|---|
| 「改…文字」「這句換掉」「加一句」「文案太硬」 | 改文字 | [改文字](#改文字) |
| 「換…那張圖」「我拍了新照片」「這張不好看」 | 換圖 | [換圖](#換圖) |
| 「顏色想暖一點」「字太小」「太擠了」 | 微調視覺 | [微調視覺](#微調視覺) |

## 改文字

1. **找到那段字。** 用 `grep` 在 `src/content/pages/*.yaml` 裡找她講的關鍵字。找不到就把該頁的內容列給她看,問「是這段嗎?」
2. **給她看改前改後。** 兩段並排,不要只講「我改好了」。
3. **她說可以之後**,改 yaml。

**紅線:文案是她的,不是你的。**
- 她說「改成 X」→ 就改成 X,不要順手潤色。
- 她說「幫我寫得順一點」→ 你可以寫,但**寫完給她看,她點頭才算數**。
- **絕對不要自己補內容。** 缺一個數字、一個年份、一個案例,而她沒給 —— 停下來問。編一個「聽起來很合理」的填進去,是這個品牌最不能踩的線。

## 換圖

1. **先跑設定**(見上)如果還沒設定過。
2. **找到她要換的是哪張。** 問清楚「首頁那張」是 hero 還是輪播裡的第幾張。不確定就開預覽指給她看。
3. **從 Drive 資料夾拿新圖**,跑:
   ```bash
   node .claude/skills/update-site/scripts/prepare-image.mjs \
     --from "<她的新圖路徑>" --to "src/assets/<分類>/<檔名>.jpg"
   ```
   這個腳本會:縮到合理尺寸、**洗掉 EXIF**(裡面有拍攝地點的 GPS,不該上公開網站)、壓縮。
4. **更新 yaml 的 `src`**,指到新檔案。
5. **寫 alt。**

**alt 這件事非常重要,而且很容易做錯:**

alt 是給看不見的人用的 —— 螢幕閱讀器會把它念出來。所以:

- **你一定要先實際打開那張圖看過再寫。** 不要照檔名猜、不要照舊的 alt 改寫、不要從她的描述推測。用 Read 工具把圖片讀進來看。
- 寫**畫面上實際有什麼**:「玻璃生態瓶裡的微景觀,苔蘚地被上臥著一隻白色小狗擺件」,不是「美麗的作品」。
- 寫錯比留空更糟 —— 留空只是沒資訊,寫錯是給錯資訊。
- schema 會擋空的 alt(`featured` / `hero` / `photos` 必填),build 會直接失敗。這是刻意的。
- 例外:首頁跑馬燈(`marquee`)的容器是 `aria-hidden`,輔助科技不會念到,所以空 alt 是對的,不用填。

## 微調視覺

**只能改 `src/styles/tokens.css` 裡已經存在的 token 的「值」。**

可以:`--bg: #FFFFFF` → `#FBFAF5`、`--t-lg: 1.25rem` → `1.4rem`
不可以:新增 token、刪除 token、改 token 名稱、改任何 `.astro` 的樣式

為什麼這麼嚴?因為 token 是全站共用的。改一個值,整個網站跟著變 —— 這正是我們要的(一致性)。但如果你新增或刪除 token,別的地方會靜默壞掉,而她看不出來。

她說「主色想暖一點」這種模糊需求 → **給她 2-3 個具體選項**(附色碼和預覽),讓她挑,不要自己決定。

## 看狀態

她問「網站還好嗎」的時候,通常是**擔心**,不是要技術報告。用兩句話回答她,不要貼 log。

```bash
node .claude/skills/update-site/scripts/publish.mjs --check   # 上次推的部署好了沒
node .claude/skills/update-site/scripts/revert.mjs --list      # 最近改了什麼
```

再開 https://verdantwanderlust-studio.github.io/ 確認站真的活著。

回她像這樣:「網站正常,最後一次改動是今天下午的關於頁文案,已經上線了。」

**不要跟她講**「build 額度」「Cloudflare 用量」這些 —— 這站跑在 GitHub Pages,
沒有那些限制。舊版的 skill 曾經這樣講,那是錯的。

## 救回來

她說「改壞了」的時候,她通常**不知道是哪一次改壞的**,也不知道「壞」的定義。所以:

1. **先問清楚壞在哪。** 「是文字不對,還是版面跑掉,還是整個打不開?」
2. **列出最近的改動給她認**,跑:
   ```bash
   node .claude/skills/update-site/scripts/revert.mjs --list
   ```
   它會用白話列出最近幾次改了什麼、什麼時候。
3. **她指認之後**,跑:
   ```bash
   node .claude/skills/update-site/scripts/revert.mjs --undo <編號>
   ```
   這會建一個「反向改動」把它退掉 —— **不是刪掉歷史**,所以之後想再拿回來還可以。
4. 退完一樣要走[預覽 → 上線](#預覽--上線)的流程。

**如果網站整個打不開 / build 失敗** —— 那不是「改壞了」,那是壞了。這種找 Jason,不要自己試著修。

## 預覽 → 上線

**每一次改動都走這個流程,沒有例外。** 這是她能安心自己改的唯一原因。

### 1. 開預覽給她看

```bash
npm run dev
```

告訴她網址(通常是 `http://localhost:4321/`),**指出該看哪一頁**(「你點 http://localhost:4321/about 看第二段」)。

不要只說「改好了你看一下」—— 她不知道要看哪裡。

### 2. 等她說可以

**她沒明確說可以,就不要上線。** 「嗯」「喔」不算。要她說「可以」「好」「上線吧」。

她說「再改一下…」就回去改,不要推。

### 3. 上線

```bash
node .claude/skills/update-site/scripts/publish.mjs --message "<白話描述>"
```

commit 訊息寫**她日後看得懂的白話**:「更新關於頁第二段文案」、「換掉首頁主視覺照片」。不要寫 `feat(content):` 這種,那是給工程師看的。

### 4. 告訴她多久會生效

推上去之後約 1 分鐘網站才會更新。跟她說一聲,不然她會以為沒成功。

想確認的話:
```bash
node .claude/skills/update-site/scripts/publish.mjs --check
```

## 你不能做的事

<important if="她的請求碰到下面任何一項">

回她:

> 「這部分需要 Jason 幫忙,我先幫你記下來。要不要我寫一個簡短的說明給你轉給他?」

然後**真的寫**那份說明,不要只是拒絕。

- 改 `.astro` / `.ts` / `.tsx` 任何程式碼檔
- 改版型、layout、結構(「這兩塊想對調」「想改成三欄」)
- 動 `src/components/MossHero.astro` —— **首頁那個苔蘚樹枝主視覺是永久保護區,一行都不要碰**
- 新增或刪除 token、改 token 名稱
- 新增頁面
- 加功能:表單、購物車、會員、訂閱、任何「按了會發生事情」的東西
- 修 build 錯誤 / 網站打不開
- 改 `astro.config.mjs` / `package.json` / `.github/workflows/`
- 改這份 SKILL.md 或 `CLAUDE.md`

</important>

**設計方向的邊界**見 `CLAUDE.md` 的「設計方向邊界」一節(禁 WebGL 流體 / 3D 植栽 / 數字跳動 / bento grid / 全站 smooth scroll)。她要那類東西 → 轉給 Jason。

注意:**首頁 hero 那個 WebGL 效果是 2026-07-17 核准的例外**,只限那一個 component。不代表其他地方可以做類似的東西。

## 測試模式

跑測試或不確定的時候,設 `DRY_RUN=1`:

```bash
DRY_RUN=1 node .claude/skills/update-site/scripts/publish.mjs --message "測試"
```

**這個網站是活的,對外的。** 一旦 push 到 main,約一分鐘後全世界都看得到。所以所有會寫入 git 或推送的腳本都吃 `DRY_RUN` —— 設了就只印出「會做什麼」,不真的做。

跑自動化測試時**一律**設 `DRY_RUN=1`。
